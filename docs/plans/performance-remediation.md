# Performance Remediation

本次改造针对两个已经确认的卡顿来源：

1. 新建任务 / 重新导入任务 / 采集结果转任务时，`xlsx` 导入和 SQLite 写入阻塞 UI。
2. 采集运行时把 Playwright 页面操作、响应解析、备份写盘放在 Qt UI 线程内，导致偶发无响应，并且随着数据量增长越来越卡。

## 总体原则

- UI 线程只负责界面展示、用户输入和轻量状态更新。
- `xlsx` 读取、SQLite 批量写入、备份写盘、Playwright 会话推进都不在 UI 线程执行。
- 任务导入与采集运行分别治理，但共用同一个架构原则：长耗时任务后台化，UI 只订阅结果。

## 任务导入改造

### 已确认问题

- 任务导入当前在主窗口同步执行。
- `openpyxl` 使用 `read_only=True` 打开工作簿后，又通过 `sheet.cell(row, column)` 逐格随机访问。
- 对于只读模式，这种访问方式会显著放大读取成本，即使 `1000 x 13` 的文件也可能让 UI 长时间无响应。

### 目标

- 任务创建、重新导入、采集结果转任务统一走后台任务创建 worker。
- Excel 读取改为顺序流式遍历。
- UI 对导入过程提供明确的“处理中”状态，不允许白屏或假死。

### 方案

- `tasks.importer` 改为使用 `iter_rows(values_only=True)`：
  - 只读取一次表头。
  - 建立列索引映射。
  - 顺序扫描后续数据行。
- 引入任务创建 worker：
  - 输入：`source_path`、`task_snapshot`、任务类型。
  - 输出：`task_id` 或错误。
- 以下入口统一复用同一个后台创建链路：
  - 主窗口新建任务
  - 任务配置保存后触发的重新导入
  - 采集结果保存后创建任务

## 采集运行时改造

### 已确认问题

- `CreatorCollectorProgressDialog` 的定时器每秒在 UI 线程调用 `session.poll()`。
- `session.poll()` 会推进 Playwright 页面动作、消费网络响应、解析 JSON、做去重、周期性写备份。
- `status()` 当前每次返回都复制整份 `rows`，随着数据增长会持续放大 UI 刷新成本。

### 目标

- 采集运行时彻底脱离 UI 线程。
- UI 获取轻量状态快照，不复制整份采集结果。
- 保存 / 导出 / 创建任务链路与采集运行时解耦。

### 方案

- 将 `CreatorCollectorSession` 放入独立子进程运行。
- 主进程与采集子进程通过 JSON 消息通信：
  - 主进程下发：`start`、`resume`、`pause`、`stop`、`save_and_create`、`update_limit`、`update_interval`
  - 子进程返回：`status`、`saved`、`created`、`error`、`interrupted`
- UI 轮询或订阅的状态对象只包含：
  - 运行状态
  - 已采集数
  - 已抓取页数
  - 上限
  - 滚动间隔
  - 时间信息
  - 最后提示
- 整份 `rows` 只保留在采集子进程内部：
  - 导出时由子进程直接写 `xlsx`
  - 创建任务时由子进程先保存文件，再调用应用层创建任务
- backup 写盘也留在子进程内部执行，避免影响 UI 事件循环。

## 实施顺序

1. 修正文档并固定改造边界。
2. 优化 `xlsx` 导入算法。
3. 为任务创建引入后台 worker，并接入三个创建入口。
4. 引入采集子进程运行时与轻量状态模型。
5. 清理采集 UI 中对整份 `rows` 的依赖。
6. 完成检查、回归和重新打包。

## 非目标

- 不改变任务模型和导出格式。
- 不改变采集结果字段结构。
- 不引入新的服务端或外部依赖。
